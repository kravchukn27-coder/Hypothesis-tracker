## PROD-062 — Сброс пароля пользователя ссылкой (для забывших/не могущих войти)

- **Status:** TODO
- **Priority:** Medium
- **Area:** Product / Auth / Users
- **Type:** Enhancement
- **Summary:** На `/users` добавить у каждого пользователя действие «Сбросить пароль» — генерирует новую ссылку установки пароля для уже активного аккаунта, по тому же паттерну «без email, ссылку копируют и передают вручную», что уже используется для приглашений.
- **Description:**
  По итогам разбора флоу приглашений (голосовой запрос, 2026-08-20): сейчас нет способа помочь пользователю, который забыл пароль или не может войти — `issueInvite` явно отклоняет повторное приглашение для уже активированного email (`"Пользователь с этим email уже активирован."` в `src/lib/auth/invites.ts`, когда `existingUser?.passwordHash` уже есть).

  Нужно отдельное действие «Сброс пароля», отдельное от приглашения:
  - Новый server action (например `resetUserPassword(userId)`), доступный из строки таблицы на `/users`, рядом с (будущей) кнопкой удаления из PROD-037.
  - Переиспользует существующий механизм `PasswordSetupToken`: инвалидирует непогашенные токены пользователя и выпускает новый с тем же TTL — как в `issueInvite`, но без блока на «уже активирован» и без создания нового `User`.
  - Ссылка ведёт на уже существующую `/invite/[token]` — страница и так работает как generic «токен → установка пароля» (имя `invite` в пути специфично для приглашений, но сам механизм универсален), включая уже реализованный повторный ввод пароля (`password` + `passwordConfirm` в `SetPasswordForm.tsx`) — эта часть уже готова, доп. работы не требует.
  - Ссылка обязана быть полным абсолютным URL — переиспользовать фикс из BUG-061, а не дублировать построение ссылки.
  - Пишет отдельное событие в `AuditLog` (например `PASSWORD_RESET_ISSUED`), `userId` — кто инициировал сброс, metadata — id/email целевого пользователя.
  - Существующие сессии пользователя не инвалидируются в момент выпуска ссылки — `sessionVersion` увеличивается, как и сегодня, только когда новый пароль реально установлен через `consumeInvite` (это уже так работает, поведение не менять).
- **Acceptance Criteria:**
  - На `/users` у каждого пользователя есть действие «Сбросить пароль», недоступное для email-не отправляющей системы иначе как через копирование ссылки вручную (без email-рассылки).
  - Клик выпускает новую полную (абсолютную) ссылку установки пароля и инвалидирует предыдущие неиспользованные токены сброса/приглашения этого пользователя.
  - Ссылка открывает уже существующую форму установки пароля с обязательным двойным вводом пароля (уже реализовано в `SetPasswordForm.tsx`, не переделывать).
  - В `AuditLog` фиксируется, кто инициировал сброс и для какого пользователя.
  - Старый пароль пользователя перестаёт работать сразу после того, как он установит новый по ссылке; новый пароль работает для входа.
  - Проверено в браузере: полный цикл — сброс с `/users` → переход по ссылке → двойной ввод нового пароля → успешный логин новым паролем, старый пароль больше не подходит.

  - Список на `/users` и колонка «Пригласил» остаются корректными для ещё не активированных пользователей (без «сломанного» отображения имени, пока оно не задано — например email как fallback).
  - `prisma/schema.prisma` не меняется.
  - Существующие проверки токена (invalid/expired/used, TTL, `sessionVersion` increment) в `invites.ts` не затронуты.
  - Проверено в браузере: полный цикл — создание приглашения только по email → переход по ссылке → ввод имени и пароля → пользователь появляется в `/users` с введённым именем.

## PROD-037 — Удаление пользователя (soft delete) с аудит-логом

- **Status:** TODO
- **Priority:** Medium
- **Area:** Product / Auth / Users
- **Type:** Enhancement
- **Summary:** Добавить на `/users` кнопку удаления пользователя. Любой пользователь может удалить любого — прав/ролей в системе нет, это осознанно. Удаление — soft delete через существующее поле `User.isActive`, событие обязательно пишется в `AuditLog`.
- **Description:**
  По итогам разбора текущей модели пользователей (голосовой запрос, 2026-08-20): удаления пользователей в системе сейчас нет вообще — ни кнопки, ни server action. Поле `isActive` в `User` (`prisma/schema.prisma`) уже существует, но никем не используется.

  Реализация:
  - Кнопка удаления в таблице на [`/users`](../../src/app/users/page.tsx) (список уже фильтруется `where: { isActive: true }`, так что после soft delete строка сама пропадает без доп. изменений в запросе).
  - Новый server action (по паттерну `src/lib/auth/invite-actions.ts`), который проставляет `isActive: false` у выбранного `User` — без физического удаления строки, без изменений схемы.
  - Прав/ролей нет — любой авторизованный пользователь может деактивировать любого другого. Не добавлять систему прав в рамках этой задачи.
  - Событие обязательно пишется в `AuditLog` через `writeAuditLog`/`safeWriteAuditLog` (`src/lib/audit-log.ts`), по паттерну `INVITE_ISSUED`/`PASSWORD_SET` в `src/lib/auth/invites.ts`: новое событие (например `USER_DEACTIVATED`), `userId` — кто удалил, `metadata` — id и email удалённого пользователя.
  - Решить при реализации (и подтвердить с пользователем, если неочевидно из UI): может ли пользователь деактивировать сам себя — по умолчанию считать, что это разрешено технически, но UI должен требовать явного подтверждения (например, диалог подтверждения) перед необратимым в текущей сессии действием, а не удалять по одному клику.
- **Acceptance Criteria:**
  - На `/users` у каждого пользователя есть кнопка удаления, требующая подтверждения перед действием (без случайного удаления одним кликом).
  - После удаления `User.isActive` становится `false`, строка данных не удаляется физически, пользователь пропадает из списка на `/users`.
  - В `AuditLog` создаётся запись о деактивации с `userId` инициатора и id/email деактивированного пользователя.
  - `prisma/schema.prisma` не меняется.
  - Связанные записи (`invitedUsers`, `hypothesisComments`, `issuedTokens`) не ломаются и не требуют каскадного удаления — они принадлежат `userId`, который просто перестаёт быть активным.
  - Проверено в браузере: деактивированный пользователь не может войти в систему — уже проверяется (`actions.ts` при логине и `session.ts` при чтении текущей сессии оба фильтруют `isActive: true`), нужно только не сломать это поведение.

## PROD-036 — Ручная сортировка (drag-to-reorder) экспериментов в столбце «Эксперимент» на Calendar

- **Status:** DONE
- **Priority:** Medium
- **Area:** Product / Calendar
- **Type:** Enhancement
- **Summary:** В таймлайне Calendar (`src/app/calendar/page.tsx`) пользователь хочет захватывать курсором строку эксперимента в левой колонке «Эксперимент» и перетаскивать её вверх/вниз внутри списка, задавая тем самым ручной приоритет отображения — независимо от текущей сортировки по датам.
- **Description:**
  Голосовой запрос пользователя: возможность вручную поднять/опустить эксперимент в списке строк Calendar, как способ задать приоритет.

  Сегодня порядок строк в Calendar — не ручной, а вычисляемый: Prisma-запрос сортирует эксперименты `orderBy: [{ startDate: { sort: "asc", nulls: "last" } }, { createdAt: "desc" }]` (`page.tsx`), и никакого поля для ручного порядка в модели `Experiment` нет (`prisma/schema.prisma`). Чтобы drag-to-reorder был устойчивым (сохранялся между перезагрузками, не конфликтовал с сортировкой по дате), нужно **новое поле** в модели `Experiment` — например `manualOrder: Int?` (или отдельная таблица порядка) — и переключение сортировки строк на это поле, когда оно задано, с осмысленным fallback на текущую сортировку по дате для экспериментов без ручного порядка. Это меняет модель данных, поэтому по правилам проекта (`docs/backlog/WORKFLOW.md`) оформляется отдельной задачей, а не как часть чисто визуальных Calendar-тикетов (UI-047…UI-053).

  Открытые вопросы для уточнения при реализации:
  - Ручной порядок — глобальный (один и тот же порядок эксперимента везде, где он показан) или локальный только для Calendar-таймлайна?
  - Как ведёт себя ручной порядок при смене окна недель (`?start=`) или при переключении в «Показать все эксперименты» (`AllExperimentsTable.tsx`, у которой уже есть собственная сортировка по колонкам, `sortBy`/`dir`) — сосуществуют ли два механизма сортировки или ручной порядок специфичен только для этого экрана?
  - Что происходит с порядком у только что созданного эксперимента (в конец списка? в начало?).
- **Acceptance Criteria:**
  - В левой колонке «Эксперимент» на Calendar-таймлайне строку можно захватить курсором (drag handle или вся строка) и перетащить выше/ниже других строк в текущем видимом окне.
  - Новый порядок сохраняется на сервере (переживает `router.refresh()`/перезагрузку страницы) — реализовано через новое поле в модели `Experiment` (Prisma) или эквивалентный персистентный механизм.
  - Порядок эксперимента без явного ручного приоритета продолжает определяться существующей логикой (`startDate` asc / `createdAt` desc), не ломается для экспериментов, которые никто не перетаскивал.
  - Drag-to-reorder не конфликтует с уже существующим drag-and-drop на этом экране — перетаскивание недатированных экспериментов на неделю (`UndatedRow` → `WeekHeaderCell`, `dataTransfer.setData("text/plain", experimentId)`) и drag-to-move/resize стадийных блоков внутри `ExperimentWeekRow` — три разных жеста должны различаться однозначно (например, по зоне захвата — drag-handle слева в колонке «Эксперимент» против самих стадийных плашек).
  - `prisma/schema.prisma` меняется только в рамках этой задачи (новое поле/таблица для ручного порядка), с `npx prisma db push` по текущему процессу синхронизации схемы (см. `docs/PROJECT_CONTEXT.md` → Local Development).
  - Поведение не переносится на Backlog/Experiments — это Calendar-специфичная сортировка, если при реализации не решено иначе (см. открытые вопросы выше).

- **Status:** DONE
- **Priority:** Medium
- **Area:** Product / Data model
- **Type:** Enhancement
- **Summary:** Хранить у эксперимента свободный текст «Раскатка» для операционного контекста в Calendar.
- **Description:**
  Добавить к эксперименту необязательное текстовое поле «Раскатка». Значение редактируется inline в Calendar и сохраняется у эксперимента; это не тег, не фильтр и не новая сущность.
- **Acceptance Criteria:**
  - Эксперимент хранит необязательное текстовое значение «Раскатка».
  - Значение можно изменить из строки Calendar без перехода на другую страницу.
  - Текст сохраняется по Enter или при уходе из поля, после чего Calendar показывает сохранённое значение; пустое значение допускается.
  - Не меняются связи гипотез, экспериментов, стадий и существующие категории тегов.
- **Resolution note:** Уже реализовано и залито ранее в рамках PROD-032
  (`Experiment.rollout`, `RolloutCell` в Calendar, поле «Раскатка» в
  `ExperimentForm.tsx`) — карточка была не отмечена. Проверено по коду:
  поле опциональное, редактируется инлайн в строке Calendar без

  после UI-032 поле стало многострочным, и Enter в нём вставляет
  перенос строки, а не сохраняет — осознанное изменение дизайна ради
  многострочного текста, а не дефект. Код не менялся.

## PROD-027 — Быстрый поиск и фиксированные рабочие срезы таблиц

- **Status:** DONE
- **Priority:** Medium
- **Area:** Product / UI
- **Type:** Enhancement
- **Summary:** Дать команде быстрый способ находить нужные гипотезы и эксперименты и открывать частые выборки без отдельной системы сохранённых представлений.
- **Description:**
  Для базы до сотен записей добавить быстрый поиск в `/backlog` и `/experiments`, работающий вместе с существующими URL-фильтрами и сортировкой. В Backlog поиск охватывает название и Comment; в Experiments — название. Добавить несколько фиксированных, понятных рабочих срезов, подходящих текущей модели (например, гипотезы без эксперимента и активные/завершённые эксперименты), но не создавать пользовательские сохранённые представления или новую модель данных. URL остаётся единственным источником состояния фильтра и поиска, поэтому любой срез можно открыть и сохранить в закладках. Массовая смена статуса явно не входит в scope.
- **Acceptance Criteria:**
  - `/backlog` позволяет быстро отфильтровать строки по названию гипотезы и Comment; `/experiments` — по названию эксперимента.
  - Поиск корректно сочетается с текущими URL-фильтрами, сортировкой, архивным видом и существующей навигацией между гипотезой и экспериментом.
  - Пустой результат поиска объясняет, что совпадений нет, и даёт понятный путь сбросить поиск/фильтры.
  - Добавлены только фиксированные системные быстрые срезы для частых рабочих сценариев; пользовательские сохранённые view, их настройка и хранение не создаются.
  - Поиск и срезы полностью кодируются в URL, остаются ссылочными и работают после перезагрузки страницы.
  - Для week-tracked экспериментов срезы по текущему статусу используют тот же источник текущей стадии, что таблица и Calendar; legacy-эксперименты используют своё скалярное поле.
  - Не добавляются массовая смена статуса, Prisma-схема, новые доменные сущности или отдельный client-side источник состояния списка.
