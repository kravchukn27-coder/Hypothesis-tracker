# Bugs

## BUG-015 — Открытая панель фильтра (Status/Funnel Level) в Backlog ломает скролл страницы

- **Status:** TODO
- **Priority:** Medium
- **Area:** UI / Backlog
- **Type:** Bug
- **Summary:** Обычно список Backlog прокручивается вместе со всей страницей. Но когда открыта панель фильтра в шапке колонки (например «Status», см. скриншот пользователя) — что-то в раскладке ломается: страница ведёт себя так, будто скроллится уже не целиком, а какой-то внутренний контейнер, и сама панель фильтра перекрывает соседние колонки (Score/Comment) вместо того, чтобы аккуратно встраиваться в макет.
- **Description:**
  Скриншот пользователя: открыт чекбокс-список фильтра «Status» (New/Planned/In progress/Accepted/Hold…) — панель шириной `w-52` наезжает поверх колонок Score и Comment, выходя далеко за пределы своей ячейки.

  Вероятная причина — в `src/components/HeaderMultiFilter.tsx` (используется и для Status, и для Funnel Level в Backlog, и для Автора в Calendar): выпадающая панель — обычный `position: absolute` `<div>` (`<div className="relative inline-block">` → `{open && <div className="absolute left-0 z-30 ...">}`), вложенный внутрь `<th>` внутри табличного контейнера с `overflow-x-hidden` (`TABLE_SURFACE_WIDTH`, `src/app/backlog/page.tsx:183`, `table-fixed`). Абсолютно позиционированный элемент, который физически шире и выше своей ячейки, вложенный в `overflow-x-hidden`-контейнер таблицы, — известный источник как раз такого рода раскладочных сюрпризов (браузер может пересчитать containing block/scroll-контекст вокруг такого элемента непредсказуемо).

  В проекте уже есть готовый паттерн, который решает именно эту проблему в другом месте: `src/app/calendar/RolloutCell.tsx` не кладёт свою панель в обычный `absolute`-div рядом с триггером, а рендерит её через `createPortal` с `position: "fixed"`, вычисляя координаты через `getBoundingClientRect()` (`anchor` в `RolloutCell.tsx`). `HeaderMultiFilter` этот паттерн не использует — вероятно, стоит перенести его сюда же, чтобы панель фильтра не зависела от overflow/scroll-контекста родительской таблицы.
- **Acceptance Criteria:**
  - При открытой панели фильтра (Status, Funnel Level в Backlog; Автор в Calendar — тот же компонент) страница продолжает скроллиться как единое целое, без переключения на скролл какого-то внутреннего контейнера.
  - Панель фильтра не наезжает поверх соседних колонок таблицы неаккуратно — либо корректно позиционируется рядом с триггером независимо от `overflow-x-hidden` родителя (например, через `createPortal`+`position: fixed`, как в `RolloutCell.tsx`), либо иначе решает конфликт с контейнером.
  - Открытие/закрытие по клику вне панели и по Escape продолжает работать как сейчас.
  - Функциональность самого фильтра (выбор нескольких значений чекбоксами, `?status=`/`?funnelLevel=`/`?calendarAuthor=` в URL) не меняется — правка чисто про позиционирование/скролл.
  - Проверить на всех трёх местах использования `HeaderMultiFilter` (Backlog: Status, Funnel Level; Calendar: Автор), так как это общий компонент и фикс один на всех.

## BUG-014 — Статус эксперимента нельзя поменять на карточке `/experiments/[id]`, и нет кнопки «убрать из календаря»

- **Status:** TODO
- **Priority:** High
- **Area:** UI / Experiments
- **Type:** Bug
- **Summary:** На Calendar статус недели можно поменять прямо кликом по ячейке. Но если провалиться внутрь карточки эксперимента (`/experiments/[id]`), статус-плашка вверху карточки — просто текст, не редактируется. Плашка должна менять статус для текущей (последней активной) недели — как это уже делает Backlog/AllExperimentsTable список. Плюс: когда статус на Calendar меняется на Done, там появляется кнопка «убрать задачу из календаря» — такой же кнопки/подсказки нет внутри самой карточки, хотя логика для этого уже есть.
- **Description:**
  Голосовой запрос пользователя: на Calendar кликом по статусу можно нормально его поменять, но при переходе внутрь карточки эксперимента статус поменять нельзя — «очень странно». По идее, плашка статуса на карточке должна редактироваться и писать в последнюю текущую (актуальную) запись недели, как это происходит с общим списком/Calendar. Плюс: на Calendar при переходе статуса в Done появляется кнопка «убрать задачу из календаря» (архивировать её оттуда) — такую же кнопку нужно добавить и внутри карточки.

  Код подтверждает это ровно так, как описал пользователь:
  - `src/app/experiments/[id]/page.tsx` — статус вверху карточки рендерится как обычный `<Badge>{stageLabel(currentStage)}</Badge>` (строки ~131-134), без `onClick`/`<select>` — чисто текст, не кликабелен.
  - Сравни с `src/app/experiments/StageCell.tsx` (используется в «Показать все эксперименты») и Backlog — там статус-плашка это `IconSelect`, который на изменение вызывает `updateExperimentStage(experimentId, next)` (`src/app/experiments/actions.ts:391`) — тот апдейтит именно **текущую неделю** (`startOfWeek(new Date())`, upsert в `ExperimentWeekStage`), а не произвольную. Именно эта функция и есть «последняя текущая запись», о которой говорит пользователь.
  - Редактирование по неделям на самой карточке технически уже есть — `ExperimentWeekStagesEditor.tsx`, отдельный список всех недель внутри формы (`IconSelect` на каждую неделю, `setExperimentWeekStage`). Но это не то же самое, что редактируемая статус-плашка вверху: пользователю нужно найти нужную (текущую) неделю в списке, а не один клик по видимому статусу карточки — отсюда и ощущение «статус нельзя поменять».
  - Кнопка «убрать задачу из календаря» уже реализована как `HideFromCalendarModal` (`src/components/HideFromCalendarModal.tsx`) и **уже подключена** в `ExperimentWeekStagesEditor.tsx` (всплывает, когда `setExperimentWeekStage` возвращает `becameDone: true`) — то есть если статус меняют через список недель на карточке, подсказка «Убрать задачу из календаря?» технически уже появляется. Но она не появляется, если статус меняют через (пока нередактируемую) верхнюю плашку — потому что верхняя плашка вообще ничего не меняет.
  - Отдельная деталь: `StageCell.tsx` (список экспериментов) при переходе в Done показывает **другую** подсказку — `ArchiveExperimentModal` (архивировать), не `HideFromCalendarModal` (убрать из календаря). То есть в проекте сейчас два разных Done-промпта в зависимости от того, откуда меняешь статус. При реализации нужно явно решить, какой из двух показывать у новой редактируемой плашки на карточке — пользователь ссылается именно на календарный вариант («убрать задачу из календаря»), так что по умолчанию логичнее `HideFromCalendarModal`, но стоит свериться с пользователем, если он ожидает архивный вариант.
- **Acceptance Criteria:**
  - Статус-плашка вверху `/experiments/[id]` (`<Badge>{stageLabel(currentStage)}</Badge>`) становится редактируемой (аналог `IconSelect`, как в `StageCell`/Backlog) вместо статичного текста.
  - Изменение через эту плашку пишет в **текущую неделю** эксперимента — тем же путём, что и `updateExperimentStage`/`setExperimentWeekStage` для «сейчас» (не создаёт и не трогает произвольную будущую/прошлую неделю).
  - После изменения статуса на карточке отражение видно сразу и на самой карточке, и (после перехода) на Calendar/в списке — без рассинхрона между `Experiment.stage`-кэшем и `ExperimentWeekStage`.
  - Если новый статус — Done, на карточке появляется тот же промпт «Убрать задачу из календаря?» (`HideFromCalendarModal`, «Да, убрать» → `hideExperimentFromCalendar`, «Нет» → `showExperimentOnCalendarWhenDone`), что уже показывает Calendar — с учётом уточнения выше про два разных Done-промпта в проекте.
  - Существующий `ExperimentWeekStagesEditor.tsx` (полный список недель) не удаляется и не ломается — новая плашка это быстрый способ поменять текущую неделю, редактор недель остаётся для остальных недель.
  - Поведение Calendar, Backlog и AllExperimentsTable не меняется — только карточка `/experiments/[id]` получает недостающую функциональность.

## BUG-013 — Новая гипотеза подсвечивается в Backlog, но страница не прокручивается к ней

- **Status:** TODO
- **Priority:** Medium
- **Area:** UI / Backlog
- **Type:** Bug
- **Summary:** После создания гипотезы (`/backlog/new`) сервер редиректит на `/backlog?saved=1&hypothesisId=<id>` (`createHypothesis`, `src/app/backlog/actions.ts`), и строка новой гипотезы подсвечивается (`isHighlighted`/`data-highlighted`/`bg-amber-50`, `src/app/backlog/page.tsx:270-275`). Но страница не прокручивается к этой строке — на длинном списке подсвеченная строка может быть вне области видимости, и пользователь не понимает, что гипотеза вообще создалась и где она в таблице.
- **Description:**
  Голосовой запрос пользователя: создаёшь гипотезу через кнопку «Создать», список подсвечивает нужную строку, но при большом количестве строк подсветка происходит вне экрана — страница не подскакивает к этому месту, и пользователь её не видит.

  Есть уже готовый компонент именно для этого — `src/components/ScrollToHighlighted.tsx` (`scrollIntoView({ behavior: "smooth", block: "center" })` на первый `[data-highlighted="true"]` элемент при монтировании), но по факту он сейчас нигде не импортируется и не рендерится (`grep -rn "ScrollToHighlighted" src/app` — пусто). Строка гипотезы в `page.tsx` уже проставляет `data-highlighted={isHighlighted || undefined}` — не хватает только смонтировать `<ScrollToHighlighted />` на странице `/backlog`, чтобы готовый механизм заработал.
- **Acceptance Criteria:**
  - После создания гипотезы и редиректа на `/backlog?hypothesisId=<id>` страница автоматически прокручивается так, чтобы подсвеченная строка была видна (центр экрана), без ручного скролла пользователем.
  - Работает и при коротком, и при длинном списке (строка вне первого экрана на момент загрузки — тоже долистывается).
  - Подсветка строки (`bg-amber-50`, `border-l-4`) не меняется — правка только добавляет прокрутку, не трогает визуальное выделение.
  - То же самое поведение (подсветка + прокрутка) распространяется на `?hypothesisId=` при переходе по «→ Эксперимент» с `/experiments`, если та ссылка использует ту же подсветку строк в `/backlog` — не создавать два разных механизма для одного и того же query-параметра.
  - Не меняются `createHypothesis`/редирект, сама логика вычисления `isHighlighted`, остальные колонки и фильтры Backlog.
